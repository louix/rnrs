# Packaging

## Packages

| Package | Purpose |
| --- | --- |
| `@rnrs/runtime` | JS runtime, spec types, native autolinking and framework Rust crates. |
| `@rnrs/cli` | The `rnrs` command: scaffold, generate, test and build. The runtime brings it into apps automatically. |
| `@rnrs/surface` | Optional React component and Rust support for rendering surfaces. |
| Your module | TypeScript spec, Rust implementation and generated interface and JS wrapper. |

Use matching framework package versions. Module packages peer-depend on the runtime and use the CLI and runtime as development dependencies. Apps install the runtime and their module packages; rendering apps also install `@rnrs/surface` directly.

See the [quickstart](quickstart.md) for authoring and [setup](setup.md#local-framework-packages) for testing package archives locally.

## Module packages

`rnrs init` writes the package fields apps need. `rnrs check` and `rnrs pack-js` (run by `npm pack`) verify them:

- React Native must resolve the package directly to `rnrs/index.ts` (through `exports`, else `react-native`, `browser`, `main`, as Metro does). With a web target, web bundlers must resolve it to `rnrs/web.ts` or `rnrs/index.ts`. Your own entry module that re-exports the wrapper is not supported.
- `npm pack` must include the spec, the crate and the wrapper. This is checked with `npm pack --dry-run --ignore-scripts` in a scratch copy; if npm cannot run, the check is skipped with a warning.
- The generated `rust/src/rnrs_interface.rs` and `rnrs/` are git-ignored by default and regenerated by `rnrs test` and `npm pack`. To commit the interface instead, remove its `.gitignore` line and run `rnrs check` in CI.
- `rnrs test` builds into `.rnrs/target` unless `CARGO_TARGET_DIR` is set.
- `@rnrs/runtime/spec` resolves in editors and `tsc` with `moduleResolution` `bundler` or `nodenext`.

`rustNative.targets` declares supported platforms. rnrs does not detect them or check that the crate's dependencies build for them. A module without `web` cannot be bundled for the browser, and its web entry throws.

## Prebuilt binaries

Module packages can ship compiled Android, iOS and browser binaries, so apps that use them need no Rust. Before `npm pack`, the author runs:

- `npx rnrs build-native --target android [--abi arm64-v8a,armeabi-v7a,x86,x86_64]` on any host. This needs Rust 1.90.0 with the Android targets and the Android NDK (`--ndk`, `ANDROID_NDK_HOME` or `ANDROID_HOME/ndk`).
- `npx rnrs build-native --target ios [--sim-arch arm64,x86_64]` on macOS. This needs Xcode, Rust 1.90.0 with `aarch64-apple-ios`, `aarch64-apple-ios-sim` (and `x86_64-apple-ios`), and Rust's `llvm-tools` component (`rustup component add llvm-tools`). `IPHONEOS_DEPLOYMENT_TARGET` defaults to 15.1.
- `npx rnrs build-native --target web` on any host. This needs Rust's wasm32 target and the pinned wasm-bindgen CLI.

The targets can be built on different machines. A run keeps the other targets' binaries only if they were built from the same sources, lock, spec and framework; otherwise it removes them. It writes `rnrs/native/`:

- `manifest.json`: the binary ABI, module name and spec IR hash, symbol, framework source hash, and a hash of every Rust source file the package ships. Per target it records rustc, minSdk (24) with link libraries and ABIs, or the iOS deployment target with the XCFramework slices.
- `android/<abi>/librnrs_<crate>.a`: one sealed object per ABI. Only `rnrs_module_v2_<crate>` stays global. Its std, Tokio, framework backend and dependencies are local, so any number of prebuilt modules link into one app.
- `ios/rnrs_<crate>.xcframework`: a static library per SDK (device arm64; simulator arm64 and x86_64), sealed the same way. Mach-O unwind info also needs the personality routine to be external, so it is exported as `rnrs_eh_personality_<crate>`. That symbol is unique to the module like the table.
- `web/rnrs_<crate>.js` and `web/rnrs_<crate>_bg.wasm`: the module as its own Wasm instance with its wasm-bindgen glue. Each instance has its own memory, allocator and native objects. The browser runtime checks the instance's web ABI, and an object from one instance passed to another is a `TypeError`.
- `Cargo.lock`: the dependency versions the binary was built with. The app's lock does not govern prebuilt modules: a dependency fix needs a module release.

`build-native --target android` builds all four ABIs React Native builds by default; `--abi` selects fewer.

A package must ship binaries matching it. `npm pack` (through `rnrs pack-js` in the package's `prepack`) fails if they were built from other Rust sources, another spec or another rnrs ABI, and warns about declared targets without binaries. `rnrs check-native` also fails on those (`--target` checks only the given targets, for an author building one platform per machine). `rnrs init` makes it the package's `prepublishOnly`, so `npm publish` refuses a package that lacks a declared target's binaries: all four Android ABIs, both iOS slices, or the web files. `npm publish <tarball>` runs no package scripts, and neither does a package without that script, so run `rnrs check-native` yourself in those cases. Modules that need `rnrs-surface` are prebuilt like any other: each binary carries its own copy of `rnrs-surface`, and the app's surface host routes every surface key to the binary that created it. An iOS surface binary records the system frameworks it links (Metal and QuartzCore among them), and the RnrsRuntime pod adds them to the app target. On the web, `createSurfaceBootstrap` binds every Wasm instance that contains `rnrs-surface`, so prebuilt surface modules need no source bundle.

Each run rebuilds every listed ABI or slice of its target and replaces earlier ones. Shipped archives carry no debug info: native crash stacks show Rust function names but no file or line. The same objects with debug info stay in the package's ignored `.rnrs/native-build/seal/` for the publisher's records. Packaging them for symbolication is not provided yet.

A module whose crate needs a framework library crate is refused, except `rnrs-surface` on Android. The native boundary is a versioned C table per module (`packages/runtime/cpp/RnrsAbi.h`). The app's `@rnrs/runtime` must have the same ABI number, otherwise the build fails before linking.

A surface module's binary carries its own `rnrs-surface` (built from the `@rnrs/surface` its package depends on), its own renderers and its own GPU device. Its module table points at that copy's surface table, which has its own ABI number (`RNRS_SURFACE_ABI`, recorded as `surface.abi` in the manifest and checked by the link step and again at startup). The app still installs `@rnrs/surface` for its platform view, but builds no Rust for it: the view's calls go to the framework, which routes each by the surface key's owner to that binary and keeps the process-wide window claims. Android binaries of surface modules also link `libandroid`. Each one adds its own wgpu and render thread.

Each prebuilt module carries its own copy of the Rust standard library and framework backend, and natively its own Rust runtime: Tokio with 2 worker threads (started on first use) and the executor budget of 32 (see [ownership](ownership.md)). Rust logging (`rustNativeApp.logging`) applies to source-built modules only.

## App builds

Android's Gradle task (`rnrsLinkModules`) and iOS's `pod install` run a Node-only step, `rnrs link`. It checks every module's prebuilt binary against the installed framework and the package's own files, then links them. It fails, naming the package, in any of these cases:

- a binary is missing for a selected ABI or SDK;
- the binary has another ABI number;
- the binary needs a higher minSdk or iOS version than the app (on iOS, React Native's minimum);
- the package's Rust sources differ from those the binary was built from (a `patch-package` edit, for example).

Nothing falls back to a source build on its own. On iOS the app target links each module's XCFramework slice for the SDK being built. Rerun `pod install` after adding modules or changing `sourceBuild`.

To compile modules from their installed sources instead, list them in the app's `package.json`:

```json
"rustNativeApp": { "sourceBuild": ["@acme/crc"] }
```

`"*"` selects every module. Listed modules are built into one bundle with cargo (Rust and the platform's targets required; on iOS by a pod script phase that exists only then), and their prebuilt binaries are not linked. Other modules stay prebuilt in the same app. Autolinking installs the native integration; module authors write no platform glue. Browser apps run `rnrs build --target web`. It checks the prebuilt binaries the same way, builds the source bundle if `sourceBuild` lists modules, and writes `.rnrs/web/rnrs.js`, which imports the source bundle and each prebuilt module's Wasm glue. Apps pass that file to `await initRnrs(modules)` before using modules; bundlers handle the `.wasm` files. Only Vite is tested.

Generated glue lives in the ignored `.rnrs/<target>/bundle/`. It references the installed module crates and patches framework crates to the copies shipped with the npm packages. Resolution checks reject a different framework copy, keeping a single runtime and surface registry per bundle.

Repeated or concurrent `initRnrs` calls with the same bundle share initialization. A failed load can be retried; a different bundle is rejected after initialization.

## Discovery and targets

The CLI walks the app's `dependencies` and installed `optionalDependencies`, resolving through Node's package layout. It does not follow development or peer dependencies. A package's `rustNative` field identifies a module and declares its supported targets: `android`, `ios`, or `web`.

Every selected module must support the requested target. Missing dependencies, duplicate module names, unsupported targets and stale generated interfaces fail with a dependency-chain diagnostic. Modules are never silently omitted. Use separate app dependency graphs when their target sets differ.

## Rust dependencies

Authors depend on `rnrs`. Its default API includes `rnrs::core`, `Native`, `CancelToken`, `TeardownScope` and `Retire`. Optional `surface` and `wgpu` features add rendering support; headless modules need neither the surface npm package nor GPU dependencies.

`rnrs test` and app builds resolve framework dependencies from the installed npm packages. Generated interfaces use the author's declared dependency name, including Cargo aliases. Direct `rnrs-core` dependencies remain supported. The dependency must be unconditional and compatible with the installed framework version.

Public npm packages use `@rnrs/*`; Rust packages use `rnrs` or `rnrs-*`.

## Rust library packages

A renderer crate depends on `rnrs-surface`, which ships in the `@rnrs/surface` npm package rather than on crates.io. Such a package declares `"rustNative": {"targets": [...], "library": {"crate": "rnrs-surface", "path": "rust"}}`. It is discovered and target-checked like a module, registers no module, and is patched into the bundle by crate name, so module crates depend on it by version (`rnrs-surface = "0.2"`, or through `rnrs`'s `surface` feature).

- The crate name must equal the Cargo package name, and the path must stay inside the package.
- `generate`, `check` and `pack-js` refuse library packages.
- **Framework crates never come from a registry.** Crates named `rnrs` or `rnrs-*` (or `rnrs_*`) are refused if their source is a registry or git, and a module depending on one that no installed package provides is refused before Cargo runs, naming the package to install.
- **Native packages must be direct app dependencies.** Autolinking links native code only for the app's direct dependencies. A selected package with native platform code (such as `@rnrs/surface`) must be in the app's `dependencies`; otherwise the Android or iOS build fails, naming the package to add.
- Multiple installed copies of one library, and libraries depending on other libraries, are not supported.

## Lock files

Commit each app's `rnrs-android.Cargo.lock`, `rnrs-ios.Cargo.lock` and/or `rnrs-web.Cargo.lock`. They survive regeneration of `.rnrs/`.

- The first build creates a missing lock. Later builds use it with Cargo's `--locked` and reject stale dependencies.
- CI should use `rnrs build --locked`, `RNRS_LOCKED=1`, or Gradle `-Prnrs.locked=true` to reject missing locks too.
- `rnrs lock --target T` reconciles dependencies while retaining locked versions. Add `--update` to upgrade within their version requirements.
- `rnrs lock --check --target T` verifies without building.

Locks contain no machine-specific paths, but do not make artifacts bit-reproducible: toolchain and SDK versions also matter. See [required tools](setup.md#tools).
